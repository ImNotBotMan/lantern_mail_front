# Архитектура веб-клиента

Одностраничное приложение на React: серверное состояние живёт в кэше запросов, экраны только
рисуют то, что пришло от API. Бизнес-правил на клиенте нет (конституция, Статья 8) — их
источник это бэкенд через `module-backend-contract`.

## Стек

React · TypeScript · Vite · React Router · TanStack Query · i18next · CSS-переменные и
CSS-модули · Vitest + Testing Library + MSW для компонентных тестов · Playwright против
живого бэкенда для сценариев сессии. Сборка — статический бандл, без SSR.

## Топология и границы

```
pages ──▶ features ──▶ api-client ──▶ API (module-backend-contract)
              │              ▲
              ├──▶ session ──┘        (session даёт токены api-client'у)
              └──▶ shared/i18n, shared/ui
```

```
src/
  app/       провайдеры (запросы, i18n, тема), роутер, layout
  pages/     экраны по адресам: вход, входящие, отправленные, письмо, друзья
  features/  доменные хуки и компоненты: letters, friends, session
  api/       client, endpoints/*, types (формы контракта)
  shared/    ui-кит, i18n-словари, утилиты
```

- **`module-front-api-client`** — единственный транспорт: базовый URL, заголовки, разбор
  ошибок, повтор после refresh. Знает формы контракта, не знает экранов.
- **`module-front-session`** — пара токенов, вход/регистрация/выход, тихий refresh при
  загрузке, guard защищённых экранов.
- **`module-front-letters`** — экраны писем и действия жизненного цикла.
- **`module-front-friends`** — поиск, заявки, список друзей, unfriend.
- **`module-front-i18n-ui`** — локализация и базовые визуальные примитивы; прикладных
  зависимостей не имеет, его используют все остальные.

Зависимости между модулями: `letters` и `friends` зависят от `api-client` и `session`;
`api-client` — от `session` (в сторону токенов) и от контракта; `session` — от `api-client`;
`i18n-ui` — ни от кого прикладного. Цикл `api-client ↔ session` разорван интерфейсом:
`api-client` получает токены и колбэк «сессия закрыта» при создании, а не импортирует session.

## Инварианты

1. **Один транспорт.** `fetch` встречается только в `src/api/client.ts`. Экраны и хуки
   обращаются к эндпоинтам через модуль API, а не к сети напрямую.
2. **Один refresh на все запросы.** Параллельные 401 ждут единственный вызов `/auth/refresh`
   и повторяются один раз. Запросы авторизации (`/auth/login`, `/auth/register`,
   `/auth/refresh`) refresh не запускают.
3. **Разлогин — только по отказу сервера.** Сессия закрывается, когда `/auth/refresh` вернул
   401 `invalid_refresh_token`. Обрыв сети, 5xx и таймаут — не повод разлогинивать: токены
   остаются, экран получает ошибку.
4. **Серверное состояние не копируется.** Кэш запросов — единственный источник данных о
   письмах и друзьях. Статус письма, `view`, допустимость действия берутся из ответа; никакого
   вычисления статуса из дат на клиенте (конституция, Статья 8).
5. **Формы контракта — в одном месте.** Типы ответов и запросов описаны в `src/api/types.ts`
   по `module-backend-contract`; экраны не разбирают JSON вручную и не объявляют свои формы.
6. **Ни одной строки в разметке.** Все тексты — из словарей `module-front-i18n-ui`.
7. **URL — состояние экрана.** Списки и письма адресуемы: `/inbox`, `/sent`, `/letters/:id`,
   `/friends`, `/account`, `/login`, `/register`.

## Решения

- **Кэш запросов вместо своего стора.** TanStack Query даёт инвалидацию после мутаций,
  повтор при возврате на вкладку и дедупликацию одинаковых запросов без ручного кода; свой
  стор на это же — больше кода и рассинхрон копий.
- **Свежесть без реалтайма.** Входящие перезапрашиваются при входе на экран, при возврате на
  вкладку (`refetchOnWindowFocus`) и по кнопке «Обновить»; у писем для этого нулевое время
  свежести — статус меняется сам по часам (`module-front-letters`). Конверт превращается в письмо при
  следующем ответе сервера. Реалтайм (SSE/WebSocket) и push — не в этой версии (не-цели в
  спеке цели); когда появятся, меняется только источник инвалидации кэша, а не экраны.
  *(Выведено как следствие решения «пока без реалтайма»; подтверждено пользователем.)*
- **Access в памяти, refresh в localStorage.** Бэкенд не ставит httpOnly-cookie, поэтому
  хранить refresh надёжнее негде; access живёт в памяти модуля сессии и не переживает
  перезагрузку — после неё выполняется тихий refresh. Так украденный из хранилища refresh
  всё равно требует действующего access, чтобы что-то прочитать.
- **Роутер с двумя guard'ами.** `RequireAuth` закрывает экраны продукта: неавторизованный
  переход ведёт на `/login` и после входа возвращает на исходный адрес. `GuestOnly` держит
  авторизованного вне `/login` и `/register`, уводя на `/inbox`.
- **Без SSR.** Клиент работает по JWT, содержимое приватное и не индексируется; SSR добавил
  бы сервер и второй способ получать данные, не дав ничего взамен.
- **Тесты.** Vitest + Testing Library на хуки и компоненты, MSW — фейковый API по формам
  контракта, поэтому тесты ловят расхождение с контрактом, а не с реализацией бэкенда.
  Сценарии, где важно поведение настоящего сервера (сессия, refresh, отзыв токенов, дружба,
  путь письма от запечатывания до прочтения), дополнительно гоняются в Playwright против живого
  бэкенда: `npm run test:e2e`, фронт
  поднимается на порту 5174, `/api` идёт через Vite-прокси на `localhost:8000`.
- **CI.** В этом репозитории (`.github/workflows/ci.yml`) на каждый PR и push в `main`
  гоняются типы, Vitest и сборка. E2E запускаются из CI монорепо: сценариям нужен живой
  backend, а его репозиторий приватный и из публичного фронтового не выкачивается.

## Модули

- `module-backend-contract` — что клиент ждёт от API (внешняя граница).
- `module-front-api-client` — транспорт, ошибки, refresh-повтор.
- `module-front-session` — токены, вход/выход, guard.
- `module-front-letters` — письма: черновик, отправка, конверт, чтение.
- `module-front-friends` — друзья и поиск.
- `module-front-i18n-ui` — локализация и UI-примитивы.
