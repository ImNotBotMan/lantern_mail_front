# API-клиент

## Responsibility

**Ответственность:** единственная точка выхода в сеть. Адрес API, заголовки, сериализация,
прикрепление access-токена, разбор ошибок в один тип, повтор запроса после обновления пары
токенов. Плюс типизированные функции эндпоинтов и типы форм контракта.

## Boundary

- Разрешено: `module-backend-contract` (формы), `fetch`, `localStorage` (только пара токенов),
  настройки окружения.
- Запрещено: React, роутер, экраны, i18n, бизнес-правила. Модуль не решает, куда вести
  пользователя и что показать, — он возвращает данные или бросает ошибку.

## Состав

- **`client.ts`** — `request(method, path, {body, form, auth})`: собирает URL, ставит
  `Authorization`, разбирает ответ, бросает `ApiError`.
- **`types.ts`** — формы контракта: `TokenResponse`, `LetterResponse`, `IncomingLetter`,
  `IncomingLetterPreview`, `UserSearchResult`, `Friend`, `FriendRequest*`, `UserResponse`, коды
  ошибок. Единственное место, где эти формы описаны.
- **`endpoints/`** — по файлу на область: `auth`, `letters`, `friends`, `users`.
- **`errors.ts`** — `ApiError` и разбор тела ошибки.

## Ключевые правила

- **Тип ошибки один.** `ApiError { status, code, message }`; `code` — из поля `error` тела,
  `message` — оттуда же. У `validation_error` сохраняется `details`. Сетевая ошибка — тоже
  `ApiError` с `status: 0` и кодом `network_error`, потому что для экранов это одна ветка.
- **Refresh — только на 401 и один на всех.** При 401 (кроме запросов авторизации) клиент
  просит сессию обновить пару, ждёт одного общего обновления, повторяет исходный запрос
  ровно один раз. Повторный 401 после успешного refresh — ошибка, а не новый цикл.
- **Отказ refresh — конец сессии.** Если `/auth/refresh` ответил `invalid_refresh_token`,
  клиент очищает пару и сообщает сессии «закрыта»; дальше экран решает роутер. Прочие ответы
  refresh (сеть, 5xx) сессию не закрывают — исходный запрос падает с ошибкой, токены остаются.
- **Токены приходят снаружи.** Клиент получает их через переданный провайдер и сам не читает
  `localStorage`: так `api-client` не зависит от `module-front-session` и цикла нет.
- **Логин — форма, остальное — JSON.** `/auth/login` отправляется `application/x-www-form-urlencoded`
  (`username` = email), это исключение из общего правила JSON.

## Ошибки, которые обрабатывает сам клиент

| Ответ | Действие |
|---|---|
| 401 на обычном запросе | refresh → повтор один раз; не помогло — сессия закрыта |
| 401 `invalid_refresh_token` на refresh | очистка пары, сессия закрыта |
| 401 на `/auth/login`/`/auth/register` | ошибка наверх как есть, refresh не запускается |
| 409 / 422 | ошибка наверх с кодом; экран показывает текст и предлагает обновить данные |
| 5xx, сеть, таймаут | ошибка `network_error` / `server_error`; сессия не трогается |

## Проверки

Тесты на MSW по формам контракта: refresh при 401 и повтор, single-flight при двух
параллельных 401, отказ refresh закрывает сессию, обрыв сети её не закрывает, тело ошибки
превращается в `code`/`message`.
