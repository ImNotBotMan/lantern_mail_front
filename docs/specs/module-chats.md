# Чаты

## Responsibility

**Ответственность:** переписка в браузере — список диалогов с превью последнего письма, лента
диалога с подгрузкой более раннего, ответ в чате и realtime-канал (`WS /ws`) поверх шины
событий бэкенда.

## Boundary

- Разрешено: `module-front-api-client` (`/conversations`, `/ws`, `/letters/*`), `module-front-session`
  (токен для сокета и refresh по 4401), `module-front-letters` (формы письма в ленте),
  `module-front-i18n-ui`.
- Запрещено: вычислять, к какому чату относится письмо, или существование чата (пара участников —
  правило сервера); собирать свой список диалогов из писем; применять дельты из события WS и
  держать копию серверного состояния (инвариант 4).

## Экраны

### `/chats`

Список диалогов одним запросом `GET /conversations`; порядок и место чата «Себе» задаёт сервер.
Строка: собеседник (у чата «Себе» — текст «Себе»), время последнего видимого письма,
превью последнего письма, метка «заморожен» при `can_write: false`.

Превью — по `preview.kind`: `text` показывает тело письма, `in_transit` — «письмо летит» без
текста и без времени доставки. `preview` есть у каждого чата: чат без видимых мне писем в
список не попадает.

### `/chats/:id`

`GET /conversations/{id}/letters` — письма в тех же трёх формах, что `/letters`, новые вперёд;
на экране переворачиваются, чтобы последнее письмо было у композера. Письмо показывается
целиком (`LetterView` / `Envelope` из `module-front-letters`): в ленте видны текст, статус,
даты и путь, отдельный экран письма для этого не нужен. Летящее чужое — конверт без текста.

- **Пагинация — курсором:** `next_cursor` уходит обратно в `before` как есть; `null` — более
  ранних писем нет. Смещения не используются: лента пополняется сверху, и `offset` дал бы дубли.
- **Прочтение — при показе.** Доставленное чужое письмо, появившееся в ленте, помечается
  `POST /letters/{id}/read` один раз на письмо (правило `module-front-letters`, без отдельной
  кнопки).
- **Ответ в чате — под лентой** (инлайн-композер): текст и кнопка «Запечатать». Композер
  только запечатывает: `POST /letters` → `POST /letters/{id}/seal`. Отправка — отдельное
  решение отправителя (жизненный цикл `DRAFT → SEALED → IN_TRANSIT`), а не продолжение
  запечатывания. Повтор после сбоя продолжает тот же черновик (с `PATCH`, если текст
  поправили), а при `invalid_state` черновик забывается.
- **Запечатанные — над композером.** В ленту чата сервер их не отдаёт, поэтому блок
  «Запечатано, ждёт отправки» берёт письма из `GET /letters/sent` (`status: sealed`, получатель —
  собеседник) и переживает перезагрузку. «Отправить» спрашивает подтверждение и делает
  `POST /letters/{id}/send`; после него перечитываются и чаты, и письма.
- **Замороженный чат** (`can_write: false`, после unfriend): история читается, композер скрыт,
  вместо него — пояснение.
- Не-участник чата получает 404 `not_found`: экран показывает «чата нет», а не пустую ленту.

## Realtime

`WS /ws?token=<access_token>` — один сокет на всё приложение, пока пользователь в продукте.
Адрес строит `api-client` (`socketUrl`), сокет живёт в `features/chats/ws.ts`.

- **Событие лишь инвалидирует кэш.** `letter.sent` / `letter.delivered` / `letter.read` не
  применяются к данным, а сбрасывают запросы: список чатов и лента диалога из события, плюс
  кэш писем. Данные приходят обычными GET'ами, поэтому повтор события безвреден.
- **4401 — только на подключении.** Сервер принимает сокет и сразу закрывает его, если токен
  не принят. Клиент отвечает как HTTP на 401: одна попытка refresh, затем переподключение.
  Если и свежий токен отвергнут — шина молчит до следующего входа, а приложение продолжает жить
  на запросах; сессию закрывает только отказ сервера в refresh (инвариант 3). Бесконечных
  переподключений с тем же токеном нет.
- **Истечение токена сокет не закрывает:** проверка только при подключении. Поэтому старый
  токен в query — норма, а `4401` приходит при переподключении после обрыва.
- **Обрыв сети** — повтор с нарастающей паузой. Пауза сбрасывается по первому сообщению сервера,
  а не по `open`: отказ 4401 приходит сразу после открытия и иначе превратился бы в частый цикл.
- **Догон — после восстановления соединения,** не при первом подключении: экраны только что
  загрузили данные сами. Что именно пропущено, неизвестно, поэтому догон сбрасывает весь корень
  чатов.
- **`conversation_id` есть у всех трёх событий** (бэкенд публикует его и при чтении). Поэтому
  событие без id — нарушение контракта, и клиент отбрасывает его как мусор, наравне с
  неизвестным типом; терять нечего: шина не источник правды, а данные догоняются запросами.
  Аварийной ветки «сбросить всё из-за события» нет — весь корень чатов сбрасывает только
  догон после обрыва.
- Keepalive: клиент шлёт `ping`, сервер отвечает `pong`; нет ответа — соединение считается
  мёртвым и переподключается.

## Данные и кэш

- Хуки — `features/chats`: `useConversations()`, `useConversationFeed(id)` (`useInfiniteQuery`
  с курсором, страница 50), `useSendMessage()`, `useReadOnShow()`, `useChatEvents()`.
  Ключи — под корнем `['chats']`: `['chats','list']` и `['chats','feed',id]`.
- После отправки сбрасываются лента и список чатов: новое письмо меняет и превью, и место
  диалога в списке.
- Загрузка, ошибка (`errors.<код>` + «Повторить») и пустой список — разные состояния;
  пусто не показывается как ошибку.

## Известные ограничения

- **Счётчика непрочитанных нет** — API его не отдаёт (определение согласовано: доставленное мне
  письмо без `read_at`).
- **Список чатов без пагинации** — контракт отдаёт все диалоги одним ответом.
- **Push в браузере нет:** события приходят, только пока вкладка открыта; пропущенное
  догоняется запросами.
- **Черновики в чате не живут:** композер сразу запечатывает письмо; распечатать, правка и
  удаление запечатанного — на экране письма (`module-front-letters`).

## Ошибки на экране

| Код | Что видит пользователь |
|---|---|
| `not_found` | «Чата нет» — диалог недоступен или пользователь не участник |
| `not_friends` | «Письмо можно отправить только другу» + обновление списка чатов |
| `invalid_state` | «Письмо уже не в том статусе» + обновление ленты |
| `sender_city_missing` / `recipient_city_missing` | «Выберите город» / «У получателя не выбран город» |
| `network_error` / `server_error` | «Не удалось загрузить» + «Повторить» |

## Проверки

- Компонентные (Vitest + MSW): список по формам контракта (включая «Себе» и замороженный чат),
  превью `text` / `in_transit`, лента с курсором, 404, прочтение доставленного, композер только
  запечатывает, отправка запечатанного — отдельно и с подтверждением, повтор после сбоя, двойной клик, события шины.
- Сокет (Vitest, подставной `WebSocket`): ping/pong, мусор в сообщении, нарастающая пауза,
  мёртвое соединение без `pong`, 4401 → refresh → переподключение, отказ refresh, отключение.
- E2E (Playwright, живой бэкенд): отправка из чата, доставка и прочтение доходят до открытых
  экранов событием шины, без перезагрузки и без «Обновить».
