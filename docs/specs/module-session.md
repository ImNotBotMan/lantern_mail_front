# Сессия

## Responsibility

**Ответственность:** пара токенов пользователя и всё, что с ней делают: вход по паролю,
вход через Google, регистрация (без сессии — до подтверждения адреса), повторная отправка
письма подтверждения, сброс пароля, тихий refresh при загрузке приложения, выход на
устройстве и на всех, признание сессии закрытой, экран аккаунта. Четыре guard'а: защищённые
маршруты, требование имени, требование города и страницы входа.

## Boundary

- Разрешено: `module-front-api-client` (эндпоинты `/auth/*`, `/users/me`), `localStorage`,
  роутер (guard, переход на вход, адрес возврата после входа), `shared/firebase`
  (окно Google — единственное, что клиент делает с Firebase SDK).
- Запрещено: экраны писем и друзей, i18n-тексты ошибок (возвращает код ошибки),
  бизнес-правила писем. Модуль не решает, что показать после входа.

## Состав

- **`tokens.ts`** — хранение: access в памяти модуля, refresh в `localStorage` под одним ключом.
  Запись/чтение/очистка пары. Хранилища может не быть (приватный режим) — тогда пара живёт
  до перезагрузки страницы.
- **`sessionStore.ts`** — состояние вне React: `loading` (идёт проверка при загрузке),
  `authenticated`, `anonymous`, текущий пользователь и ошибка проверки; методы `login`,
  `loginWithGoogle`, `register`, `resendVerification`, `requestPasswordReset`, `logout`,
  `logoutAll`, `updateUser`, `closeSession`. Здесь же мост для `api-client` (access,
  refresh, «сессия закрыта»), который тот получает при создании, — поэтому цикла
  `api-client ↔ session` нет.
- **`GoogleSignInButton.tsx`** — кнопка «Продолжить с Google» вместе с окном Firebase и
  разбором его отказов. Не рендерится, если проект Firebase не настроен (`shared/firebase`
  без ключей в окружении): кнопки, которая падает при клике, не бывает.
- **`VerifyEmailNotice.tsx`** — экран «проверьте почту» с адресом и повторной отправкой
  (с паузой, чтобы сервер не засыпали письмами).
- **`useSession.ts`** — доступ экранов к состоянию через `useSyncExternalStore`. Состояние
  живёт вне React, потому что закрыть сессию может `api-client` — вне дерева компонентов.
- **`guard.tsx`** — четыре guard'а: `RequireAuth` (пока `loading` — заглушка, при `anonymous` —
  переход на `/login` с сохранением исходного адреса), `UsernameRequired` (без имени — на
  `/choose-username`), `CityRequired` (без выбранного города — на `/city`) и `GuestOnly`
  (авторизованного уводит со страниц входа на `/inbox`). Тихая проверка сессии запускается
  из `RequireAuth` и `GuestOnly`.
- **`navigation.ts`** — адрес возврата после входа: сохранённый guard'ом, иначе `/inbox`.

## Ключевые правила

- **Bootstrap при загрузке.** Есть refresh-токен → тихий `/auth/refresh`, затем `/users/me`;
  нет или отказ — `anonymous`. Приложение не мигает экраном входа, пока идёт проверка.
  Проверка одна на вкладку: повторный refresh отозвал бы пару, которую только что выдал
  предыдущий, поэтому guard'ы запускают её через модульный флаг.
- **Сеть при bootstrap не разлогинивает.** Отказ пришёл по сети или 5xx — состояние остаётся
  `loading` с ошибкой, экран показывает её с кнопкой «Повторить», пара токенов на месте.
- **Пара меняется только вместе.** Каждый refresh возвращает новую пару, и клиент сохраняет
  её целиком: старый refresh после этого недействителен, а его повторное предъявление сервер
  считает кражей и закрывает всю сессию.
- **Автоматический разлогин — только по отказу сервера** (инвариант 3 архитектуры).
- **Регистрация сессии не открывает.** `POST /auth/register` отвечает 202 и токенов не даёт:
  без подтверждённого адреса входа нет ни одним способом. Экран переключается на «проверьте
  почту» с адресом, на который ушло письмо.
- **Повторная отправка письма — это повтор входа.** Сервер отправляет письмо на каждой
  попытке входа без подтверждения, поэтому отдельного эндпоинта нет: кнопка «Отправить ещё
  раз» повторяет `POST /auth/login` с теми же email и паролем, которые экран ещё держит в
  состоянии. Если адрес уже подтвердили, этот же повтор просто входит — экран уводит в
  продукт. Пауза между повторами — 60 секунд.
- **Вход через Google.** `signInWithPopup` → `getIdToken()` → `POST /auth/firebase` → та же
  пара токенов и то же состояние, что после пароля. Закрытое человеком окно — не ошибка
  (ничего не показываем); заблокированное окно и ненастроенный провайдер — отдельные тексты;
  отказ сервера (`email_registered`) показывается как код контракта.
- **Имя спрашивается один раз.** Пришедший через Google выбирает `username` на шаге
  `/choose-username` (`PATCH /users/me`), и `UsernameRequired` не пускает дальше ни в город,
  ни в продукт. У зарегистрировавшегося по паролю имя уже есть, шаг он не видит.
- **Сброс пароля.** Форма на экране входа: email → `POST /auth/password/reset` → «письмо
  отправлено» всегда, даже для незнакомого адреса (существование аккаунта не раскрывается).
  Письмо и страницу смены пароля отдаёт Firebase.
- **Явный выход срабатывает всегда.** Кнопка «Выйти» очищает пару локально сразу и лишь
  затем пытается `/auth/logout`: пользователь, попросивший выйти, не остаётся внутри из-за
  обрыва сети. Цена решения: если запрос не дошёл, refresh-токен живёт на сервере до
  истечения срока и остаётся в списке сессий — локальный выход его не отзывает.
  *(Выведено как следствие UX-ожидания «вышел — значит вышел»; подтверждено пользователем.)*
- **Выход во всех сессиях** — отдельное действие (`/auth/logout-all`) с подтверждением:
  отзывает сессии на всех устройствах, включая мобильные. Порядок обратный явному выходу:
  сначала запрос к серверу (для него нужен access-токен), затем локальная очистка; ошибка
  сервера оставляет сессию открытой и показывается на экране.
- **Одна сессия в браузере, но несколько вкладок.** Вкладки не синхронизируются через
  события хранилища в первом билде: рассинхрон ограничивается тем, что каждый refresh
  обновляет `localStorage`, а неудачный — закрывает сессию в своей вкладке.
- **Возврат на исходный экран.** После входа пользователь попадает туда, куда шёл до
  редиректа на `/login`; без сохранённого адреса — на `/inbox`. Дальше решают guard'ы: без
  имени — `/choose-username`, без города — `/city`.
- **Авторизованный на страницах входа.** `/login` и `/register` закрыты `GuestOnly`: тот,
  у кого сессия жива, оказывается на `/inbox` и формы не видит.
- **Продукт требует имя и город.** `UsernameRequired` и `CityRequired` стоят между
  `RequireAuth` и layout'ом продукта, а сами `/choose-username` и `/city` лежат вне
  соответствующего guard'а внутри `AuthLayout`: это уже не вход, но ещё не продукт.
  Правила зеркалят сервер (по имени адресуют письма, без города письмо не отправить), но не
  подменяют его: отказ всё равно придёт от API.
- **Экран аккаунта** показывает `username`, дату создания, город профиля с действием
  «Изменить», «Выйти» и «Выйти на всех устройствах».

## Пользователь видит

- Экраны `/login` и `/register` — отдельный layout: логотип, переключатель языка (он нужен
  до входа) и форма по центру.
- Форма входа: email, пароль, «Забыли пароль?» и кнопка «Продолжить с Google» под формой
  (кнопки нет, если Firebase в окружении не настроен). Форма регистрации: email, `username`
  (3–32, `[a-z0-9_]`), пароль (8–128) и та же кнопка Google — те же ограничения, что
  проверяет сервер, чтобы не отправлять заведомо неверное.
- Экран «Проверьте почту»: адрес, объяснение, что без подтверждения входа нет, и кнопка
  «Отправить ещё раз» с обратным отсчётом.
- Экран `/choose-username`: одно поле имени и предупреждение, что изменить его потом нельзя.
- Сброс пароля — тот же экран входа в режиме одной формы: email → «Письмо отправлено» и
  возврат ко входу.
- Ошибки входа (`invalid_credentials`) и регистрации (`email_taken`, `username_taken`) — под
  полем, по коду ошибки; `email_registered` при входе через Google — баннером над формой;
  остальные коды — тоже баннером.
- Экран `/account`: `username`, дата создания, город профиля с действием «Изменить», «Выйти»
  и «Выйти на всех устройствах». Пока недельный лимит смены не истёк, вместо кнопки — строка
  «Город можно изменить с <дата>». Подтверждение выхода на всех — inline на странице.

## Проверки

Тесты на MSW: bootstrap с валидным refresh и без него; отказ refresh → `anonymous`; обрыв
сети при bootstrap → остаётся `loading`/ошибка, но не разлогин; повторный bootstrap не
предъявляет refresh дважды; guard возвращает на исходный адрес и уводит без имени на
`/choose-username`; вход и регистрация показывают коды ошибок под своими полями; регистрация
показывает «проверьте почту», а повтор входа после подтверждения ведёт в продукт; вход по
неподтверждённому адресу открывает экран письма; Google меняет ID-токен на сессию, закрытое
окно молчит, отказ сервера показывается баннером; сброс пароля просит только email; «выйти»
очищает пару даже при обрыве сети. Окно Firebase подменяется в `test/setup.ts` — в jsdom его
не открыть.

E2E на живом бэкенде (Playwright, Chrome; `npm run test:e2e`; бэкенд — на `localhost:8000`):
вход с возвратом на запрошенный адрес, регистрация, неверный пароль, выход с проверкой после
перезагрузки, «выйти на всех» с отзывом сессии во втором браузерном контексте. Прогон идёт
против бэкенда **без Firebase**: там фейковый провайдер подтверждает адрес сам, иначе вход
в e2e был бы невозможен без ящика почты. Сценарии с живым Firebase (Google, письмо
подтверждения) в CI не автоматизируются и проверяются вручную.
